# `TODO.md` как живой технический roadmap

В Agent Compass `TODO.md` — это не плоский чеклист. Это живой технический документ между Архитектором, разработчиками и AI-агентами.

Он одновременно работает как:

- roadmap фаз разработки;
- лог архитектурных решений;
- контейнер для статус-апдейтов;
- источник контекста для техлида и субагентов;
- список человеческих задач, если часть работы нельзя выполнить агентом.

Если обычный TODO — это стикер, то этот формат ближе к design doc + wiki + kanban.

## Source of truth

Источником истины по задумке проекта должны быть дизайн-документы, а не сам `TODO.md`. TODO отвечает за план исполнения, статус и ближайшие решения, но не должен подменять product/design intent.

Типичные source-of-truth документы:

- `doc/design-doc.md`
- `doc/<project>-design.md`
- `doc/<subsystem>-design.md`
- `doc/decision_log.md`
- ADR-документы

В преамбуле TODO стоит явно ссылаться на такие документы, чтобы агент понимал: если roadmap и design doc расходятся, нужно остановиться и поднять конфликт, а не молча выбрать удобную версию.

## Заголовок и преамбула

Файл начинается с короткого контекста: что это за проект, откуда взят план и какие документы являются source of truth.

```md
# TODO — <Название проекта>

План работ для <краткое описание продукта> на основе `doc/design.md`, `README.md` и `AGENTS.md`.
```

Преамбула должна помогать агенту быстро понять, почему задачи сгруппированы именно так.

## Фазы и волны

Работа обычно организуется в именованные фазы:

- `Фаза N`
- `Alpha N`
- `Wave N`
- тематический раздел без строгого номера

Фаза может означать порядок выполнения, как в roadmap, или тематическую область, как в kanban. В начале проекта порядок чаще важен; позже TODO может стать гибридом roadmap и kanban.

```md
## Фаза N. Название фазы

**Цель:** Одно предложение о результате этой фазы.

- [ ] Реализовать X: что входит в scope и зачем это нужно.

**Критерий завершения:** Пользователь может сделать Y, а CI подтверждает Z.
```

Критерий завершения должен быть проверяемым. "Готово" или "реализовано" не подходят.

## Out of scope

Крупный TODO должен явно говорить, что намеренно не делается.

```md
### Out of scope

- Полная миграция schema до MVP.
- Новый внешний admin portal.
- Fine-tuning собственной модели.
```

`Out of scope` снижает риск того, что агент расширит задачу и начнёт строить лишнюю архитектуру.

## Формат задач

Задачи пишутся через чекбоксы, но не как короткие одноразовые строки. Формулировка должна быть достаточно подробной, чтобы через месяц не приходилось угадывать смысл.

```md
- [ ] Реализовать X: описание смысла задачи, зачем она нужна и что именно входит в scope.
  - [ ] Подзадача первого уровня.
    - [ ] Подзадача второго уровня с конкретной деталью реализации.
```

Многострочные задачи полезны для группировки близких требований без создания новой фазы.

## Inline статус-апдейты

Закрытые задачи или задачи в процессе могут содержать статус прямо под чекбоксом.

```md
- [x] Сделать горячую перезагрузку конфигурации без рестарта процесса.
  - **Статус (2026-04-19):** реализовано; список параметров зафиксирован в `doc/runtime.md`.
```

Формат даты: `YYYY-MM-DD`.

Если задача обновлялась повторно:

```md
- [x] Обновить runtime policy.
  - **Статус (2026-04-19, обновлено 2026-04-21):** политика отражена в `AGENTS.md`, тесты добавлены.
```

Статус должен фиксировать полезный контекст: что сделано, где смотреть, какие ограничения остались.

## Приоритеты

Приоритет удобно писать прямо в тексте задачи, а не выносить в отдельную таблицу.

```md
- [x] **Высокий приоритет:** Провести аудит prompt surface.
- [ ] ***P0*** Критическая блокирующая задача — берётся первой.
- [ ] ***P1*** Разблокирует другие задачи или даёт измеримый выигрыш.
- [ ] Низкий приоритет: спроектировать X.
```

Практический default:

- обычный приоритет не указывается явно;
- высокий и низкий приоритет пишутся текстом;
- `P0/P1/P3` допустимы, если проект уже использует такую шкалу, но текстовые маркеры часто удобнее для чтения.

## Комментарии Архитектора

Если автор хочет добавить мнение, гипотезу или контекст, не смешивая это с задачей, используйте отдельный вложенный комментарий.

```md
- [ ] Добавить metadata block в KB-файлы.
  - _Комментарий Архитектора_: Предполагаю, что нужны поля `chat_id`, `chat_name` и опциональный `timezone`.
```

Комментарий не равен требованию. Агент должен оценить его и, если есть trade-off, явно указать это перед реализацией.

## GATED-задачи

Если задачу нельзя брать без условия, помечайте её как `GATED`.

```md
- [ ] Оптимизировать X *(GATED)* — поднимать только после измерения latency > 200 ms.
  - [ ] **Gate:** требуется telemetry report и benchmark baseline.
```

Это защищает roadmap от premature optimization и от работы без нужных данных.

## Перенос и отказ от задач

Не удаляйте задачи, от которых отказались, если причина важна для будущего. Перечеркните и добавьте объяснение.

```md
- ~~Реализовать SSAO в Alpha 2.~~ *(Перенесено в Alpha 4.2; текущий стек даёт слишком тёмную сцену.)*
```

Так TODO сохраняет память о решениях и не заставляет будущего агента заново проверять уже отвергнутую идею.

## Ссылки

Задачи должны активно ссылаться на контекст:

- документы: `doc/design.md`, `AGENTS.md`, `BUGS.md`;
- тесты: `tests/router/test_foo.py::test_bar`;
- ADR: `doc/decision_log.md#adr-001-hybrid-architecture`;
- смежные репозитории: `G:\GitHub\AskVLM`;
- upstream issues или forum threads, если они важны для решения.

Ссылки превращают TODO в рабочую карту, а не в изолированный список пожеланий.

## Экосистема TODO-файлов

Один проект не обязан ограничиваться одним `TODO.md`.

| Файл | Назначение |
|---|---|
| `TODO.md` | Основной roadmap по продуктовым фазам |
| `CI_TODO.md` | Задачи по локальной CI, линтингу, покрытию и проверкам |
| `REFACTORING_TODO.md` | Технический долг и подготовительные refactor-slices |
| `TODO_<scope>.md` | Roadmap отдельной подсистемы, например `TODO_userbot.md` |
| `TODO_legacy.md` | Архив старых задач, которые ещё могут вернуться |
| `DONE.md` | Завершённые задачи, которые полезно хранить как контекст |
| `BUGS.md` | Отдельный трекер известных багов |
| `Roadmap.md` / `OpusRoadmap.md` | Отдельный крупный roadmap для больших проектов, если `TODO.md` уже выполняет роль оперативного канбана |

`TODO_legacy.md` полезен для проектов, где старые задачи ещё могут вернуться, но не должны шуметь в актуальном roadmap. Более общепринятый `DONE.md` лучше подходит для завершённых задач, которые нужны как исторический контекст.

В особо крупных проектах могут параллельно существовать `TODO.md` и отдельный `Roadmap.md`: первый используется как оперативный рабочий список, второй хранит крупную долгосрочную карту продукта или технической эволюции.

## Человеческие задачи

Если часть работы требует ручного действия, держите её явно:

```md
## Человеческие задачи до первого запуска

- [ ] Получить API key и положить его в секретное хранилище.
- [ ] Проверить права бота в production-чате.
- [ ] Выполнить ручной smoke test после деплоя.
```

Техлид должен переносить задачи из `Manual Changes Required` в такой список, если работа ведётся по TODO-like документу и пользователь просит сохранять человеческий backlog.

## Notes / Appendix

В конце больших TODO-файлов полезен раздел `## Notes`.

Туда попадают:

- обоснования архитектурных решений;
- сравнительные таблицы альтернатив;
- ссылки на референсы и anti-references;
- планы эволюции по фазам;
- объяснение, почему roadmap устроен именно так.

`Notes` — это не задачи. Это память решений, которая помогает агентам не повторять старые споры.

## Как агент должен работать с TODO

- Читать преамбулу, фазы, `Out of scope` и критерии завершения до начала реализации.
- Не считать закрытый чекбокс достаточным доказательством: проверять статус, diff, тесты и CI.
- При выполнении задачи обновлять чекбокс и добавлять inline status, если это создаёт полезный будущий контекст.
- Не закрывать ручные задачи, если агент их не выполнил фактически.
- Не удалять спорные или отменённые задачи без разрешения Архитектора.
- Если задача неоднозначна, задать вопрос или вынести trade-off в отчёт, а не silently выбрать удобный scope.

## Ключевое отличие

| Обычный TODO | Живой TODO Agent Compass |
|---|---|
| Плоский список коротких строк | Иерархия фаз, подзадач и критериев |
| Нет контекста "зачем" | Каждая задача объясняет цель и scope |
| Статус только `[x]` | `[x]` + inline status с датой |
| Один файл | Экосистема roadmap/CI/refactoring/bugs/done |
| Нет архитектурной памяти | `Notes` и комментарии Архитектора |
| Нет явного "не делаем" | `Out of scope` как первоклассная секция |
| Нет приоритетов | Текстовые маркеры или `P0/P1` прямо в задаче |
