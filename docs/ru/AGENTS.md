# Концепция `AGENTS.md`: операционный контракт проекта

`AGENTS.md` — это документ для AI-агента, который объясняет, как работать именно в этом репозитории. Его задача не продать проект человеку, а сделать работу агента воспроизводимой: куда смотреть, что не трогать, какие инварианты соблюдать и какую проверку обязательно запустить перед финальным отчётом.

## `README.md` и `AGENTS.md`: разделение ролей

- `README.md` — витрина проекта и стартовый How To для человека.
- `AGENTS.md` — производственный контракт исполнения для AI-агента.
- `CONTRIBUTING.md` — правила участия в проекте для людей.
- `TODO.md` / `CI_TODO.md` / `REFACTORING_TODO.md` — рабочие планы, которые агент может читать как текущую задачу или roadmap.

Не стоит перегружать `README.md` внутренними операционными деталями. И наоборот: не превращайте `AGENTS.md` в маркетинговое описание проекта. Люди могут читать `AGENTS.md`, но его главный читатель — агент.

## Что должно быть в `AGENTS.md`

### Доктрина

Начинайте с 1-3 проектных инвариантов, которые агент обязан учитывать до написания кода. Это не советы, а ограничения на дизайн решений.

Пример:

```md
## Доктрина

- Максимальная производительность
- Соответствие включению в [реестр ПО] в соответствии с [регламентом.md]
```

Доктрина снижает риск "правильного, но неприемлемого" решения: агент сразу видит, какие варианты запрещены даже если они проще.

### Порядок чтения

Дайте агенту короткую карту документации: что читать первым и зачем.

```md
## Порядок чтения

1. `README.md` — обзор продукта и пользовательский контекст.
2. `TODO.md` — актуальный roadmap и открытые задачи.
3. `doc/architecture.md` — архитектурные решения и термины.
4. `CI_TODO.md` — план локальной CI, если задача касается проверок.
```

Для больших документов полезно указывать секции или диапазоны строк. Это не должно превращаться в полный индекс: достаточно маяков, которые экономят агенту первые итерации поиска.

### Code Map

Code Map говорит агенту, где находится основной код и какие области отвечают за крупные подсистемы.

```md
## Code Map

- `src/` — основной код приложения.
- `tests/` — unit/integration тесты.
- `tools/` — проектные утилиты.
- `doc/` — архитектурная документация и ADR.
```

Выносите в Code Map верхнеуровневые пути, которые редко меняются. Слишком детальная карта подпапок быстро устаревает и вводит агента в заблуждение.

### Read-only зоны

Если в репозитории есть зоны, которые нельзя изменять без явного разрешения, объявите это явно.

```md
## Read-only зоны

- Не изменяй содержимое `vendor/` и `third_party/`.
- Не редактируй сгенерированные файлы вручную; меняй генератор.
- Не трогай субмодули. `.gitmodules` можно читать только для понимания путей.
```

Эта секция особенно важна для больших репозиториев, где агент может попытаться "починить" vendor-код или сгенерированные артефакты.

### Локальная CI и финальная верификация

`AGENTS.md` должен содержать явную команду финальной проверки. Без неё агент легко заканчивает работу по принципу "выглядит нормально".

~~~md
## Контроль качества

- Перед финальным отчётом запусти локальную CI:

```powershell
./run.ps1 -Fast -SkipLaunch
```

- Если задача затрагивает release-critical поведение, используй полный прогон без `-Fast`, если это принято в проекте.
- Если CI не удалось запустить, укажи причину в `Unfulfilled Tasks` или `Manual Changes Required`.
~~~

Команда должна быть конкретной. Не пишите "запусти тесты" без указания entrypoint: агент выберет случайный уровень проверки.

### Глоссарий

В больших проектах полезно держать короткую выжимку терминов, которые постоянно встречаются в задачах.

```md
## Глоссарий

- runner — `run.ps1`, тонкая точка входа локальной CI.
- orchestrator — `build.ps1`, слой стадий и отчётности.
- curated KB — вручную проверенная база знаний проекта.
- raw archive — неизменяемый журнал исходных событий.
```

Глоссарий должен быть компактным. Полный словарь лучше держать в отдельном документе и ссылаться на него.

## Project policy vs user policy

Универсальные правила поведения агента лучше держать в User Rules или аналоге системного prompt-а. Пример: безопасность, формат отчёта, комментарии, языковые стандарты и запрет на подавление багов.

`AGENTS.md` должен хранить проектно-специфичный слой:

- как устроен этот репозиторий;
- какие команды проверки здесь используются;
- какие зоны нельзя менять;
- какие документы являются source of truth;
- какие runtime-инварианты нельзя нарушить.

Если агентная система не передаёт User Rules субагентам, добавьте в `AGENTS.md` или в prompts для субагентов явный bootstrap:

```md
Важно: следуй правилам, встроенным в карточку субагента, а в самом начале работы полностью прочти `AGENTS.md` для project-specific контекста.
```

## Минимальный шаблон

~~~md
# AGENTS.md

## Доктрина

- <проектный инвариант 1>
- <проектный инвариант 2>

## Порядок чтения

1. `README.md` — <зачем читать>.
2. `TODO.md` — <зачем читать>.
3. `doc/...` — <зачем читать>.

## Code Map

- `src/` — <что здесь>.
- `tests/` — <что здесь>.

## Read-only зоны

- <что нельзя менять>.

## Контроль качества

- Перед финальным отчётом запусти:

```powershell
./run.ps1 -Fast -SkipLaunch
```

## Глоссарий

- <термин> — <краткое значение>.
~~~

## Анти-паттерны

- Дублировать весь `README.md`.
- Делать `AGENTS.md` учебником по языку программирования.
- Поддерживать две разные копии общих AgentCompass-правил в нескольких репозиториях.
- Перечислять каждую подпапку, если эта карта устареет через неделю.
- Писать "запустить тесты" вместо конкретной CI-команды.
- Прятать read-only ограничения в длинных абзацах вместо явного списка.
- Обновлять `AGENTS.md` только после релиза: он должен меняться вместе с реальными operational contracts.
